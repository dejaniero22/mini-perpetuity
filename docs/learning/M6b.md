# Learning Note: M6b (approver role)

- **Why one role was not enough.** Everything shared the everyday role, so "the MCP server cannot approve" was only a statement about the server's code. The fix is to move the power into the database: a second role that can do the trusted things, whose password the human types. Then "who is allowed" is decided by PostgreSQL, not by which code path was taken.
- **`mp add` was the other open door.** Making `approve` strict would have been pointless while `mp add` could write approved memory with the same role. The design closes both: the everyday role can only create *pending* memory.
- **Triggers need the caller's role.** The guards use `pg_has_role(current_user, '<approver>', 'MEMBER')`. This is also true for superusers, so the admin connection and the test fixtures keep working without special cases. Checked directly against PostgreSQL 18.7 before relying on it.
- **Trigger order matters for tests.** A `BEFORE INSERT` trigger fires before CHECK constraints, so an old test that expected a CHECK failure from the everyday role now gets the trigger's refusal first. Constraint tests now run as the approver (the role that can reach them); a separate group tests what the everyday role cannot do.
- **The wrong-tense bug.** The first working version printed "rejectd #2". Building a past tense by appending "d" works for "approve" only. The real-terminal test caught it; a mock would not have.
- **Testing a password prompt for real.** `tests/helpers.py` runs the CLI as a subprocess with a pseudo-terminal and types the password when the prompt appears. It also starts every subprocess in a new session so there is no controlling terminal: a test can never reach, or hang on, the terminal pytest was started from, and it matches an AI's shell tool, which has no terminal either.
- **`getpass` flushes typed-ahead input.** Writing the password into the pseudo-terminal before the prompt appears loses it, so the helper waits for the prompt text first.
- **An empty password is a trap.** libpq treats `password=""` as "not given" and falls back to `PGPASSWORD` and `~/.pgpass`. The CLI refuses an empty entry, and a test proves that a correct `PGPASSWORD` in the environment does not rescue an empty or wrong typed password.
- **Mutations found two missing tests.** Weakening the code 14 ways showed that nothing tested (a) that the CLI decides a batch in one transaction, and (b) that the password is never sent to the server as text. Both tests were added before the final run.
- **Limits that remain** are in [ADR-M6b](../decisions/ADR-M6b-approver-role.md): active tampering by something running as your OS user, confidentiality, unauthenticated ordinary audit entries, and online password guessing. A different OS user or machine for the approval step is the next level, not built.
- **Verified.** 330 tests pass on a local PostgreSQL 18.7 source build (290 earlier tests, kept green by moving trusted-memory fixtures to the approver connection, plus 40 new), with Ruff, mypy `--strict`, pip-audit and gitleaks. Fourteen deliberate weakenings (no insert guard, everyday role keeps its update grant, everyday role can decide, no event guard, approval through the everyday role, password from the environment, no terminal check, empty password allowed, no length check, no repetition check, plaintext password sent, commit per item, `mp add` creating approved memory, unknown ids ignored) each made tests fail, then were reverted.
- **For M7.** `mp doctor` should check that the everyday role has no update privilege, that the approver exists and has a password, and warn if the approver password file or environment variable ever appears. The default `mp_<name>_approver` name is derived, not configured.
