# Learning Note: M6

- **Quarantine in two layers.** Code: `propose.py` can only create `proposed` rows, `review.py` is the only approval path, and a test starts the MCP server module in a fresh interpreter and asserts `mini_perpetuity.review` was never imported. Database (migration 0006): a trigger refuses any INSERT attributed to a `client:` agent unless it is a proposed `ai_inference` or `summary`; the update guard allows exactly two changes (expire a live approved version; decide a pending proposal). Mutation checks removed each layer separately and tests failed each time, so neither layer is carried by the other.
- **A test fixture was wrong, not the trigger.** An older test inserted *approved* rows attributed to `client:test`. The new trigger correctly refused that, since real AI rows always start as proposals. The fixture now inserts a proposal and decides it.
- **Why a DB trigger and not a CHECK constraint.** A CHECK ("client rows must be proposed") would also fail when the owner later approves, because CHECKs apply to updates too. A BEFORE INSERT trigger applies only to creation.
- **Rate limiting reused the ledger counters** from M5: `memory.propose` events count toward the per-client quota. A size cap alone does not stop a client from adding many small proposals, so there is also a cap of 50 pending proposals per client (my addition, easy to change; it frees up as you decide).
- **Reviewing hostile text.** `mp review` prints AI-written text. Control characters are replaced and every content line is prefixed with `| `, so a proposal containing a fake `#99 ...` header, a fake "Approve:" footer or ANSI escapes cannot impersonate the tool. A test feeds exactly that.
- **"human_decision event".** I read the plan's wording as a ledger event with that activity name (payload: decision, id, reason, proposed_by), not a new memory object. Rio to confirm. **[Inference]**
- **The limit that matters:** the database cannot distinguish your CLI from a shell, because they share the app role, which needs `UPDATE (status)` for approvals to work. A client with shell access as your OS user could approve its own proposal with SQL. Quarantine holds for clients that only use the MCP server. The stronger design (a separate approver role whose password is typed, never stored) is described in ADR-M6 and not built. **[Inference]**
- **Other limits.** An approved proposal's `recorded_at` is its proposal time (the decision time is in the ledger). Proposals are always `normal` sensitivity. A well-formed but wrong note is still approvable: review is the control.
- **Verified.** 290 tests (M1 to M6) pass on a local PostgreSQL 18.7 source build, plus Ruff, mypy `--strict`, pip-audit and gitleaks. Fifteen deliberate weakenings (client may approve, no insert guard, DB allows any expiry or re-opening, proposals not quarantined in code and DB, no pending cap, no size limit, no required source, no seatbelt, server imports the approval code, decision without a reason or without authorization, unsanitized review output, no decision audit, quota ignoring proposals) each made tests fail, then were reverted.
