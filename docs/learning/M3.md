# Learning Note: M3

- **Two timelines, two interval pairs.** Valid time (`valid_at`..`invalid_at`, true in the world) and system time (`created_at`..`expired_at`, known to the system), both half-open. `as_of(valid_on, known_on)` filters on both. The test builds a synthetic history where the *same* valid date gets different answers depending on `known_on` (before vs after a correction), plus the boundary instant where the old version expires and the new one is born (exactly one answer).
- **A correction is a new row plus one expiry.** `correct_object` locks the old row (`FOR UPDATE`), inserts the new version (`supersedes = old id`), and sets `expired_at = now()`/`status = 'superseded'` on the old one, all in one transaction. Both use `now()` (transaction time), so the old version's expiry equals the new version's creation: no gap, no overlap. Ending validity (`invalid_at`) is also a correction, not an in-place update.
- **"Nothing is updated in place" at the database level.** The app role can `INSERT` only the descriptive columns (not `id`, `created_at`, `expired_at`), can `UPDATE` only `expired_at` and `status`, and a trigger narrows even that to "expire a live version, once". `DELETE`/`TRUNCATE` are refused by privilege and by a statement trigger. `UNIQUE (supersedes)` keeps version chains linear. For `id`, PostgreSQL refuses earlier (the column is `GENERATED ALWAYS`).
- **Provenance and epistemic types as constraints.** Activity and agent are required and non-empty. `source_record`, `extracted_claim`, `ai_inference` and `summary` must carry a `was_derived_from` pointer (INV-10: a pointer, not a copy). The seven types are a CHECK list; an unknown type is rejected.
- **Seatbelt** (`seatbelt.py`): SSN-shaped numbers, private-key headers, AWS key ids, `password/secret/token/api_key = value`. It runs before anything is written, never echoes the matched text, and has no override flag. **[Inference]** It can reject harmless text and miss real secrets; it is a seatbelt only.
- **Ledger.** `mp add` and corrections write `memory.add` / `memory.correct` events in the *same transaction* as the change (a failed insert leaves no event). Event payloads hold ids and types, never content.
- **Limits.**
  - The admin/owner role can insert any `created_at` and edit anything (tests rely on this to build history). System time is trustworthy only as far as the admin role is.
  - A zero-row `UPDATE` is not refused (the guard is row-level; unlike the ledger there is nothing to protect).
  - `mp add` creates `approved` objects: it is the human path. AI-written `proposed` objects and the approval step are M6.
  - **You cannot read memory back through the tool yet.** Retrieval is M4 and the MCP server is M5; `correct_object` has no CLI (the plan lists only `mp add`). To inspect data now, query as the admin role.
  - `sensitivity` has two values (`normal`, `sensitive`); what they gate is decided in M4+. **[Inference]**
- **Verified.** All 117 tests (M1 to M3) pass on a local PostgreSQL 18.7 source build. Four deliberate weakenings of the migration (no guard trigger, wider grants, no provenance rule, no uniqueness) each made tests fail, then were reverted.
