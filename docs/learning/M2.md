# Learning Note: M2

- **Two layers, as in ADR-0016 layers 1-2.** The app role has `SELECT` and `INSERT` on `events` only; a trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` for anyone it applies to. Tests cover both: without grants the statement fails with *insufficient privilege*; with `GRANT ALL` on the table it still fails, now from the trigger (*restrict violation*).
- **Statement-level trigger.** A row-level trigger lets `UPDATE ... WHERE false` through silently. The single `BEFORE UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` trigger refuses those too, and one trigger covers `TRUNCATE` (which cannot be row-level).
- **Guard cannot be switched off by the app role** (tested, including with `GRANT ALL`): `ALTER TABLE ... DISABLE TRIGGER`, `DROP TRIGGER`, `DROP TABLE`, replacing the trigger function, and `SET session_replication_role = replica` (the classic bypass) all fail with *insufficient privilege*.
- **Known limit (MB3 answered):** the table owner, which is the admin role used by `mp admin`, can disable the trigger and change the ledger. A test records this on purpose (`test_owner_can_disable_the_trigger_documented_limit`). Anyone holding `MP_ADMIN_DSN` or a PostgreSQL superuser login can rewrite history. Layer 3 (outside the database) is not in the mini. **[Inference]** Keep the admin DSN out of AI clients and shell history.
- **Instance stamp.** `events.instance` must equal the database's own instance name: a `CHECK` calls `instance_name()`, which reads `instance_meta`. It is checked on insert only; the ledger being immutable is what keeps it true afterwards.
- **`mp admin migrate <name>`** applies migrations an existing instance has not seen (each in its own transaction, recorded in `schema_migrations`). Migration SQL uses `{app_role}` as a placeholder for the instance's role. It refuses a database whose `instance_meta` names another instance.
- **How it was verified.** All 63 tests (M1 + M2) ran locally on PostgreSQL 18.7, built from the `REL_18_7` git tag in the authoring sandbox without ICU, and in CI on the digest-pinned Docker image. A mutation check (deleting the trigger from the migration) made 7 ledger tests fail, so the tests do detect a missing guard.
- **Not verified:** behaviour under server settings that differ from defaults; the CI image and local build differ slightly (18.6 Debian build vs 18.7 source build, ICU off). The ledger has no `occurred_at` ordering guarantees beyond `id`.
