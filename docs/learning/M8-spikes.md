# Learning Note: M8 spikes

- **A spike answers a question, not a feature.** Each script exists to turn one "[U]" in ADR-M8 into a fact, with the smallest code that can. They live in `spikes/`, outside the package, and change no product behaviour.
- **MB18 was testable here and changed the design.** A non-superuser role with `CREATEDB CREATEROLE` ran `init-instance`, all migrations and `set-approver`, and could not touch roles it did not create. Two details mattered: a separate backup role is unnecessary (the everyday role can already dump since migration 0008), and the setup role *owns* the tables, so it could switch off the ledger's guard triggers. That is the concrete reason it may be unlocked only per action, never held by the running UI.
- **Instances revoke `CONNECT` from everyone.** A read-only role that holds `pg_read_all_data` still gets "permission denied for database" until it is granted `CONNECT` on that one instance. The isolation from M1 is doing its job; it also means a cluster-wide backup role would weaken it, which is another reason not to add one.
- **A name-constrained CA is checkable without a browser.** OpenSSL rejects a certificate from the spike CA for `example.com`, a look-alike `personal.localhost.evil.com`, or a non-loopback IP ("permitted subtree violation"). The constraint is written into the CA certificate, so the one-time trust you grant on the Mac is limited to localhost names, at least for verifiers that honour name constraints. Whether every macOS browser does is the open part of MB17.
- **Delete the CA key at once.** The spike signs one 7-day leaf and never writes the CA key to disk. Trusting a CA is a standing decision; a key that does not exist cannot leak.
- **Do not set HSTS in a spike.** A browser that remembers HTTPS-only for a `localhost` name would break other local tools later. The spike sets no `Strict-Transport-Security` header (a test asserts that); the real UI decides this in M8a.
- **The page cannot send anything.** `connect-src 'none'`, no `fetch`, no inline script; the report is shown in a text box for you to copy. Tests assert all three, so the spike cannot quietly become a data path.
- **A real browser run found nothing the unit tests missed, and that is still worth knowing.** Headless Chromium untrusted: certificate error; with the error ignored: all three names load, secure context, `__Host-` cookie works; a virtual authenticator returns PRF output that is stable for one salt and different for another. This proves the page logic, not Touch ID.
- **One command silently did not apply.** A scripted edit looked for code that Ruff had already reformatted, matched nothing, and the new MB18 steps were missing until a test checked their names. Assert that a replacement matched.
- **Verified.** 363 tests pass (355 earlier plus 8 new), Ruff, mypy `--strict`. Twelve deliberate weakenings (CA constraint widened for DNS or for IPs, bind to all interfaces, TLS 1.2 allowed, no Host check, CSP allowing connections, HSTS added, key file mode 0644, 400-day certificate, a `fetch` in the page, setup role made superuser) were each caught by a test, then reverted. One first appeared to survive because my edit changed nothing; it was redone.
- **Result on a real Mac.** Chrome 157 accepted the name-constrained certificate after the one-time trust step, all three `.localhost` names loaded, and each address held only its own cookie. A walkthrough in plain steps worked for someone not using a terminal daily.
- **A requirement can remove a spike.** Rio asked for password-only approval (not every device has a fingerprint reader; accessibility). That made the passkey test pointless, so it was deleted rather than finished. Fewer features, fewer things to keep working.
- **Cross-platform is a real cost.** The browser side is portable; the server uses Unix-only pieces (`pwd`, `/dev/tty`, permission bits). Whether to pay for Windows is a decision, not a default (MB24).
- **Not verified.** Safari, Firefox, Windows, the optional PostgreSQL role test on Rio's machine.
