# Learning Note: M1

- Isolation is two layers: separate DB per instance with `CONNECT` revoked from `PUBLIC`, and a separate role granted `CONNECT` on its own DB only. Tests check every ordered pair of three instances.
- `CREATE DATABASE` cannot run in a transaction, so `init-instance` is not atomic; on failure it drops the DB/role and removes the files it wrote (tested).
- `ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` applies to objects later created by the same admin role, in that database. It does not retroactively change existing functions.
- Known leak: app roles can still connect to the shared `postgres` database (PUBLIC has `CONNECT` there) and can see the *names* of other instance databases/roles in the catalogs. Not changed in M1; touching system databases is invasive. **[Inference]**
- `instance_meta` stores the instance name in each database; `mp status` refuses if it disagrees with the config (guards against a config pointing at the wrong database).
- The generated password is written to a `0600` file next to the config (placeholder until ADR-M3 decides Keychain vs file). The password also appears in the `CREATE ROLE` statement sent to the server, so it can show in server statement logs if `log_statement` is on. **[Inference]** (not checked)
